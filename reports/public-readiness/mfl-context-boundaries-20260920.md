## Reproduced failures and correction

- **High — cross-account private state:** raw league cache was keyed only by league/year; transports reread whichever app token was current; saved credentials and session API keys lacked owner provenance. A newly signed-in account could inherit A's private connector key. Raw cache now includes initiating account, connection and explicit API key; every asynchronous boundary rechecks a captured sticky scope. Saved records/pointers are per owner, with a separate exact owner/league marker for the volatile key. Unknown legacy records remain untouched and require an explicit reconnect. B cannot overwrite A's saved franchise/selection. A returning after B can restore its selection, but must re-enter a private key if the single-tab key now belongs to B.
- **High — selected league/season and incomplete data:** credentials could override the selected target, unrelated raw identities could map into the requested league, and missing rules/rosters/player data could become connected success. The provider validates supplied identities, complete declared franchises and rosters, unique/usable player directory, and usable settings/scoring before caching or mapping. It validates the selected franchise. These checks establish the observed core payload contract; they do not prove arbitrary provider scoring features or optional-feed completeness.
- **High — late publication and writes:** legacy connect mutated `S` before private followups finished. All publication now occurs synchronously after final context checks. Login/lineup transports capture token/context, validate targets and shard host, bound header plus body reading to20s, and reject stale completions. A write timeout reports an **unknown outcome**, requires checking MFL, and does not retry. Previously acquired in-memory login cookies are context-bound; durable cookie ownership remains a separate public caller dependency.
- **Medium — save truthfulness:** connection persistence previously swallowed storage errors. New synchronous writes verify their result, attempt rollback of attempted keys, and throw an actionable failure. As with browser storage generally, a persistent failure can also prevent rollback; callers must not claim saved on any failure. Malformed/unknown records do not silently fall back to another flat key.

The public player-universe request is league-independent and now carries neither league ID nor private API key. It remains cached by season after shape validation. Crosswalk selection is season-bound. Historical transactions remain under `w0` rather than falsely claiming they all occurred in the current week. Their content/status truthfulness is still open below.

## Caller contract / required integration

- `MFL.fetchLeague(id, year, apiKey, { isCurrent, timeoutMs })`; optional `isCurrent` is a synchronous caller-account/request/view predicate. Timeout is capped at20s. `mapToSleeperState(raw, id, year)` rejects stale/mismatched module-returned raw objects.
- `MFL.provider.connect(creds, options)` produces canonical IDs and owner-tagged `_platformCreds`; `hydrate(league, ctx)` preserves `ctx.sleeperPlayers` plus the same current-view/deadline options. Supplied `_platformCreds` must belong to the current owner.
- `provider.saveCredentials(key, { leagueId, year, apiKey, franchiseId?, _mflOwner? })` returns true only after confirmed synchronous writes; it rejects an explicitly supplied different owner. `loadCredentials(key)` and `loadConnection()` return only owned records or throw a reconnect message for unknown/mismatched legacy state. `currentOwner()` and `isConnectionCurrent(creds)` expose stable local identity consistency, **not server authorization**.
- New local keys: `mfl_creds_v2:<encoded-owner>:<leagueKey>`, `mfl_connection_v2:<encoded-owner>`, compatibility `mfl_connection_owner_v1`. Tab keys: `mfl_api_key_context_v1`, `mfl_guest_owner_v1`. Guest ownership is created only by an explicit connect/save, never by loading old credentials. Authentication transitions must clear volatile connector context; retained owner-scoped metadata must not be reassigned.
- `mflLogin(opts)` and `submitLineup(opts)` accept optional `isCurrent`/`timeoutMs`. A lineup requires explicit valid league/year/week/franchise and unique mapped starter IDs. Caller must recheck context before storing a returned login cookie or publishing success. Unknown restored cookies cannot be authenticated to an app owner by this module alone.

Parent owns `app.js` corrections. Actual callback baseline in `tests/mfl-public-caller-baseline.cjs` reproduces A's delayed cloud connection installing keys after B signs in, and a pending12345/2025 franchise choice mixing with a newer99999/2026 flat connection. Required fix: capture account/request before cloud access, gate before each write/server followup, keep selected target and account with the pending result, finalize against its own franchises, and use the owned-record API. Automatic flat-key reads must not bypass it. Our next separate public branch owns `lineup.js` cookie ownership/late response recovery. Shared owner correctness must ship with these caller changes; no premature consumer pin.

Further official-document review found that `TYPE=lineup` import names the selected franchise with `FRANCHISE_ID`; the previous implementation used `FRANCHISE`, which is used by export requests. The write URL now uses the documented import parameter and the actual positive-write fixture asserts its value and the absence of the old field. No real import was attempted. The server remains responsible for owner/commissioner authorization. The initial new <=18 client week cap was also removed because the provider documentation does not establish it; positive two-digit week validation remains, avoiding a speculative restriction on supported provider seasons.
